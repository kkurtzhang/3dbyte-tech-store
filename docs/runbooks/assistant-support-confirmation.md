# Assistant support confirmation and history

The model tool `createSupportTicket` prepares a draft only. It returns a random proposal ID, expiry and `confirmation_required`; it never receives a confirmation receipt. The customer selects **Review support request**, sees the exact support inbox, reply email, name, subject, message, category/priority, references and summary, then explicitly selects **Send support request**. Conversation excerpts are excluded by default. Selecting the checkbox obtains a new preview/receipt and displays the excerpt before sending.

## Trust boundary

The browser transcript is untrusted. One canonical text representation drives routing and generation; contradictory `content` and text parts, unsupported roles/parts, oversized messages and envelopes fail validation. Historical tool results/inputs/approvals, sources, reasoning and provider metadata are discarded. Normal text conversation and newly executed tools in the current stream remain available. The local knowledge path uses the same message schema. Current or consequential evidence must be fetched again.

The Next confirmation endpoint requires JSON, exact configured same-origin checks, the HttpOnly SameSite=Strict session cookie and rate limits. HTTPS/production cookies use the `__Host-` prefix and Secure attribute. Browser correlation IDs do not authorize anything. A context digest incorporates the server-read session and existing customer-token cookie. Medusa independently validates a supplied customer bearer token, rejects invalid tokens without falling back to guest, and binds the proposal to that actor. Customer/order IDs and verified-order metadata cannot be supplied by the model or confirmation body. Guest order references stay unverified. An authenticated order association additionally requires ownership and matching reply email, checked again at submit.

`POST /ai/support-ticket/prepare` stores a bounded draft for ten minutes. `POST /ai/support-ticket/preview` derives current associations and returns a two-minute receipt only to the direct UI. The receipt binds a SHA-256 digest of the exact canonical payload, recipient configuration, customer/session context and transcript choice. Refreshing the preview rotates it. `POST /ai/support-ticket` accepts only proposal ID, receipt, digest and explicit confirmation; missing, forged, expired, changed, cross-session and replayed receipts cannot create a ticket or notification.

Redis compares the entire prior snapshot and atomically claims it once, checking receipt expiry at the claim. The Medusa module creates ticket, first message and consent event using one native transaction context. Existing notification idempotency keys apply after persistence. Saved status can be read through preview; a repeated submit returns conflict without another write. Receipts stay out of chat history, provider requests and telemetry. Responses are not cached.

## Configuration and release gates

This uses the existing backend `REDIS_URL`, `INTERNAL_API_TOKEN`, customer authentication and support notification configuration. No dependency, signing secret, credential or access grant is added. Two additive migrations add a nullable `ai_consent_proposal_id` and a concurrent unique index. Existing tickets need no backfill; uniqueness includes soft-deleted tickets. The column/index are deliberately forward-only to preserve consent audit and replay protection on application rollback. Production also requires the existing storefront `NEXT_PUBLIC_SITE_URL` to match its browser origin. Redis must already permit GET, SET with NX/PX, PTTL, TIME and EVAL on `assistant:ticket-consent:v1:*`. Missing configuration, unavailable Redis or denied commands fail closed. Obtain separate authorization if an environment needs an ACL/configuration change; do not silently grant it.

Apply the additive migrations through the normal Medusa migration runner before enabling the backend confirmation gate. The support module exports a scoped `runMigrations` entrypoint using the pinned native connection/migrator. Its `allOrNothing: false` commits each migration separately: the unchanged historical table migration commits before the new nontransactional column migration, then the unique index builds concurrently outside a transaction. Other modules and the application's database settings are unchanged. This follows [MikroORM's concurrent-migration transaction guidance](https://mikro-orm.io/docs/migrations). Successful earlier migrations remain applied if a later migration fails; inspect migration history before recovery.

Verify PostgreSQL reports `IDX_support_ticket_ai_consent_proposal` both valid and unique after rollout. An interrupted concurrent build can leave an invalid index: rerunning intentionally fails rather than silently skipping it. Inspect the index, migration history and any duplicate proposal IDs; preserve ticket/consent audit records. An operator must approve a targeted invalid-index repair and resolve the cause before rerunning the normal migration command. Never mark the failed index migration complete or enable confirmation with an invalid index. Measure lock/build behavior on representative data before release.

Deploy the backend confirmation gate before the storefront so old clients fail safely; deploy the storefront promptly afterward to restore the new handoff UI. No deployment is authorized by this document. Normal contact-form and Admin ticket paths are unchanged. Reverting only the storefront fails closed; reverting the backend alone restores the previous consent gap and must not be used as a routine rollback.

## Failure and recovery

Once claimed, a proposal is never released automatically. If database/network outcome is uncertain, the UI removes the send control and requires a fresh status check. The ticket transaction now persists `consent_context_hash` and the exact confirmed `consent_support_inbox`. Preview checks PostgreSQL by unique proposal ID before consulting Redis, compares the original session/account context, and returns only ticket identity/status plus notification status. It does not send notifications or expose contact details. This works after Redis completion failure, expiry or loss while the original browser session/account binding still exists. A different account/session, an expired browser cookie or a soft-deleted ticket requires operator help; it cannot bypass the binding.

After a successful commit, a Redis completion error does not hide the saved ticket. Both notification intents are now committed with the ticket in an append-only delivery journal. The new [AI ticket email status and authorized recovery runbook](support-notification-recovery.md) is authoritative for per-recipient pending/queued/sent/failed/unknown states, original-recipient preservation, Admin visibility and separately authorized reconciliation/retry. A legacy queue acknowledgement is not proof of delivery or permission to resend.

The isolated PR247 reconciliation drill exposed a pinned-native retry failure: a failed notification could reach the provider on retry, then fail to update its record and remain marked failed. This follow-up avoids replaying that row. It records uncertainty before external dispatch and requires verified non-acceptance plus confirmation that the original sender has stopped before a separately authorized new attempt. Unknown outcomes never retry automatically. Status reads send nothing. The app does not independently verify a provider's external evidence and does not promise exactly-once delivery.

There is no background retry worker or recurring operational commitment. Pending or uncertain outcomes require deliberate Admin inspection and the guarded workflow. Existing confirmed tickets without a delivery journal remain unknown until reconciled; missing original-recipient metadata blocks recovery rather than redirecting mail to a current environment value.

Redis is required for new consent and atomic claims; PostgreSQL is authoritative for saved status. A unique proposal index prevents a second ticket even if stale Redis state revives a spent receipt, including soft-deleted rows. This requires a valid index and preserved PostgreSQL commits. Do not restore consent keys from stale backups. Independent security review of this revised head and deployed origin/proxy/Redis checks remain release gates. No live ticket or email is used for implementation verification.

## Isolated verification

Run the affected storefront assistant suites and backend support suites using the workspace scripts. CI's test job provisions ephemeral PostgreSQL 16 and Redis 8.4 services bound to loopback and runs the native regressions. Locally, explicitly provide `CONSENT_TEST_POSTGRES_URL` pointing to the isolated loopback fixture's `/postgres` administrator database without a password, plus `REDIS_URL` and `CONSENT_TEST_REDIS_URL` for an isolated loopback Redis. Without the explicit fixture URL the native suite is skipped. Never set these to a live service.

`consent-native.unit.spec.ts` calls Medusa's module migration entrypoint against new synthetic databases, checks fresh/upgrade/idempotent/failure behavior, then loads the actual native service. It tests concurrent confirmation, a committed-ticket Redis-completion interruption, context-bound durable status with Redis unavailable, a crash-before-queue pending state, durable duplicate rejection and transactional rollback of an invalid initial message. Notifications are mocked. Each run preserves its created databases and prints their names; no tables/data are dropped, and no Redis keys are deleted/flushed. The smaller Redis CAS suite separately verifies real atomic claims. Browser evidence uses installed local Google Chrome, a fresh isolated profile and actual confirmation components with synthetic responses; production cookie/proxy configuration and real provider delivery need separately authorized validation.
